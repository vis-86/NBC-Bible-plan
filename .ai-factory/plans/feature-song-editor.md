## Решения Игоря (2026-09-21) — не пересматривать

1. **Общий каталог, правка видна всем сразу.** Никаких черновиков и «версий общины».
   Конфликт двух редакторов — last-write-wins. Для общины в десяток музыкантов этого
   достаточно, а второе состояние песни стоило бы лишних полей, экранов и пути синхронизации.
2. **Ink-пометки якорятся по СОДЕРЖИМОМУ строки, а не по её индексу.** Правка соседних
   строк не двигает чужие пометки; правка самой строки теряет её пометки явно.
   Существующие пометки требуют миграции.
3. **Ввод — вставка «аккорды над строкой» + тап, а не редактирование ChordPro.**
   Музыкант никогда не видит квадратных скобок. ChordPro остаётся форматом хранения.
   Обоснование и отвергнутые альтернативы — в разделе «UX-модель» ниже.
4. **Запись — online-only**, с явным UI «нужен интернет», по образцу сетлистов.
   Осознанное исключение из offline-first: каталог общий, и offline-запись через
   LWW-outbox молча затирала бы чужую правку. Чтение остаётся полноценно офлайновым.

## UX-модель (проверена интерактивным прототипом)

Прототип: `.ai-factory/design/song-editor-prototype.html` (перенести из скретчпада, см. T0.3).

- **Вставка (90 % случаев).** Музыкант копирует песню с холихордса — это monospace
  «аккорды над строкой». Конвертер разбирает её сам. Ручное выравнивание аккордов
  пробелами на телефоне невозможно в принципе — это главная причина, почему «просто
  textarea» как редактор не работает.
- **Аккорд — абсолютно спозиционированный слой НАД строкой, не инлайн-элемент.**
  Инлайн-аккорд при перетаскивании переливает текст под пальцем.
- **Клавиатура аккордов вместо системной.** Семь ступеней тональности песни готовыми
  кнопками + переключатели `m · 7 · maj7 · sus4 · sus2 · add9 · /бас` + хроматика за «Ещё».
  Барьер, который это снимает: набрать `F#m` на русской раскладке — три переключения.
- **Тап ставит аккорд, drag двигает.** Аккорд заперт в своей строке (одна ось — один
  смысл, потерять аккорд невозможно). Перенос на соседнюю строку — дискретными ↑/↓
  в панели выбранного аккорда, без прицеливания.
- **Проекции импульса у drag нет намеренно.** Формула Apple (`v/1000·d/(1−d)`) рассчитана
  на бросок шторки через экран: на 560 px/s даёт +280 px, и аккорд улетает в конец строки.
  Расстановка аккорда — точная задача, как курсор в тексте: цель по точке отпускания.
  Скорость при этом уходит в пружину посадки, чтобы не было шва.

### T0.4 — Парсер теряет текст без метки секции ⚠️ ПРЕДУСЛОВИЕ для T3

Найдено 2026-09-22 при работе над T1. `parseSongBlocks` (`songParser.ts`) не создаёт блок,
пока не встретит `{comment:}`:

- песня **без единой метки** → `[]` → `SongView` рисует **пустой лист**;
- текст **до первой метки** молча выбрасывается.

В проде не всплывало: все 97 песен корпуса начинаются с метки (проверено скриптом — задетых
песен ноль). M9 это меняет: музыкант вставит короткую песню без «Куплет:» и после сохранения
увидит пустоту. Замысел в коде был другим — `songSectionKind.ts` прямо говорит «первая
секция песни бывает без `{comment:}`» и отдаёт ей `other`; парсер этот случай просто
не реализует.

Починка: текст до первой метки (и песня без меток целиком) становится секцией без метки.
Для существующих песен ничего не меняется — у них текста до первой метки нет, значит
индексы секций и якоря пометок не сдвинутся. **Перед починкой проверить не репозиторий,
а прод-Directus:** песни могли добавлять в обход корпуса.

Не чинилось в рамках T1 сознательно: это правка рендера ВСЕХ песен, а не якорей.

✅ **Сделано 2026-09-22.** Из `parseSongBlocks` убран флаг `hasStartedFirstBlock`: текст до
первой метки стал блоком `{ comment: '', kind: 'other' }`, три копии сброса блока свёрнуты
в `flush()`. Ведущие пустые строки и директивы (`{key:}`, `{start_of_chorus}` …) блока

## T1 — Якоря пометок по содержимому строки ✅ сделано 2026-09-22

Не закоммичено. Реализация:

- `src/features/songs/lib/inkLineHash.ts` — хэш строки (FNV-1a → base36), индекс хэшей
  тем же разбором, что у `SongView`, и `resolveStrokeAnchors`.
- `useSongInk` получил опцию `content`: якоря приводятся к текущему тексту ДО состояния,
  поэтому `toAbsolute`, `strokeIndex`, `LineRenderer` не менялись вообще. Страница песни
  передаёт `song.content` — после «Песня обновлена» пометки пересаживаются сами.
- Сироты держатся в отдельном ref и дописываются при сохранении.
- `SongStroke.anchor.hash` необязателен; в zod-схеме записи поле объявлено явно.

Отличия от исходного замысла, найденные по ходу:

- **Хэш без аккордов — не всегда.** Строка из одних аккордов (вступление, проигрыш) без
  аккордов пуста и слиплась бы со всеми пустыми строками, поэтому её личность — сами
  аккорды. Правка аккордов такой строки её пометки сиротит — это осознанно.
- **zod молча резал хэш.** `z.object` отбрасывает неизвестные ключи: без явного поля
  в `songState.schemas.ts` хэш терялся бы на каждой записи, и на втором устройстве
  (или после перезагрузки с сервера) якорь снова держался бы только за индекс.
  Закрыто тестом `songState.schemas.test.ts`.
- **Политика сирот уже была.** `toAbsolute` возвращал `null` для отсутствующей строки
  ещё до M9 — не рисовать сироту умел существующий код; новым стало только то, что
  сирота не ложится на чужую строку по старым индексам и переживает сохранение.

**Проверено:** 16 тестов модуля (включая выбор среди двух одинаковых строк припева —
тест специально построен так, чтобы оба штриха НЕ прошли быстрым путём), 3 теста хука
(хэш у нового штриха, выживание сирот, пересадка при новой версии текста), 3 теста схемы.
Весь набор — 1217 тестов зелёные; линтер на затронутых файлах чист; `tsc` без новых ошибок.

**Осталось — миграция существующих пометок, см. T4.1.** Хэш старому штриху дописывается
лениво — в памяти при открытии песни и в хранилище только при следующем сохранении
пометок владельцем. Если редактор поправит песню раньше, чем владелец старых пометок её
откроет и сохранит, те разрешатся по индексу и могут съехать.

### Исходный замысел T1 (для истории)

1. Функция хэша строки — рядом с `inkAnchor.ts` (единственный источник имён якоря).
   Вход — нормализованный текст строки (без аккордов: `chordProToPlainText` уже умеет);
   выход — короткая стабильная строка. Хэш обязан быть устойчив к правке аккордов:
   музыкант, поправивший аккорд, не должен терять свои пометки.
2. `SongStroke.anchor` получает **необязательное** поле хэша. Необязательное — потому что
   в проде уже лежат пометки без него (IDB `songState` + Directus `song_user_state`).
3. Разрешение якоря, в порядке:
   - точное совпадение хэша, ровно одно → берём его;
   - совпадений несколько (повторяющиеся строки припева — обычное дело) → ближайшее
     к сохранённому индексу;
   - совпадений нет → строку правили, пометка **осиротела**;
   - хэша нет вообще (старая запись) → прежнее поведение по индексу, хэш дописывается
     при следующем сохранении.
4. Политика осиротевших: **не рендерим, но из хранилища не удаляем.** Удалять нельзя —
   правка может быть откачена, и тогда пометки должны вернуться. Логировать `console.debug`
   с количеством.
5. Тесты: правка соседней строки пометки не двигает; правка самой строки их сиротит;
   повторяющиеся строки не «склеивают» пометки; старая запись без хэша читается.

**Приёмка:** `npm run test` зелёный; отдельный тест на песню с двумя одинаковыми строками.
