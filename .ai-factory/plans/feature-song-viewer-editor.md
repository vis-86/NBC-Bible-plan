# Song viewer/editor — autonomous implementation plan

Источник требований: `docs/song-viewer-spec.md`. Ветка: `chordpro-viewer`.

Каждый запуск (в т.ч. автономный, из cloud routine) начинает с чистого чекаута — **этот файл единственный источник прогресса**, обновляй Progress Log перед завершением сессии.

> **Внимание: номер этапа в этом плане НЕ равен номеру раздела спеки.** Спека — это документ с разделами §0–§14, а не пошаговый роадмап. У каждого этапа ниже явно указано, какие разделы читать. Не открывай «§N» по номеру этапа.

## Правила для автономного агента

### Границы
- Работай ТОЛЬКО в ветке `chordpro-viewer`. Никогда не трогай `main`, `deploy/`, прод-конфиги, `.env*`.
- Никогда не выполняй `npm run deploy`. Никогда не меняй прод-Directus (коллекции, поля, права, схему) — это ручная работа Игоря.
- Не переписывай типографику аккордов (`tokenizeChord` в `ChordRenderer.tsx`, `chordSign*` в `songs.css`) без явной задачи — она прошла ручную проверку на реальном корпусе.
- Держись рамок задачи: попутные улучшения — записью в Progress Log, а не коммитом.
- Не добавляй абстракции, флаги конфигурации и обработку невозможных случаев без явного запроса.

### Секреты
- `.env.test` gitignored и в свежем клоне его нет. Если тесты его требуют — создай с **фиктивными** значениями по списку из `ENV_SETUP.md` (`NEXT_PUBLIC_DIRECTUS_URL`, `DIRECTUS_ADMIN_TOKEN`, `TELEGRAM_BOT_TOKEN`, `NEXT_PUBLIC_BASE_PATH`, `SESSION_SECRET`, `INVITE_ADMIN_SECRET`, `NEXT_PUBLIC_APP_URL`). Не коммить.
- Никогда не коммить и не печатать реальные секреты. Встретил в выводе — маскируй (`sk-***`) перед тем как класть куда-либо, включая Progress Log.

### Верификация (без этого этап не готов)
1. `npm run test` — всегда зелёный (на 2026-07-25: 67 файлов, 383 теста).
2. `npm run lint` — **линтер на ветке УЖЕ красный по унаследованному долгу: 59 errors, 30 warnings в 41 файле** (в основном `no-explicit-any`, `ban-ts-comment`, setState-in-effect). Добиться нуля НЕЛЬЗЯ и НЕ НУЖНО — это не твоя задача, чинить чужой долг = выход за рамки.
   Критерий: прогони `npm run lint` **до** начала работы, запомни числа; после правок числа не должны вырасти, а в файлах, которые ты трогал, ошибок быть не должно. Если базовое число изменилось не из-за тебя — зафиксируй в Progress Log.
3. Тронул offline/SW/кэширование/роутинг — дополнительно: `npm run build` → просмотреть сгенерированный `out/sw.js` → `npm run e2e:offline` (см. `CLAUDE.md`, dev-режим эти баги не ловит).
4. **Playwright в чистом окружении:** браузеры не ставятся через `npm ci`. Перед `npm run e2e:offline` выполни `npx playwright install --with-deps chromium`. Если установка не проходит (нет root, нет сети) — **правка НЕ считается проверенной**: не пиши «готово», зафиксируй в Progress Log строкой `E2E НЕ ПРОГНАН: <причина> — нужен локальный прогон Игоря` и не закрывай этап галочкой.
5. При падении проверки чини причину, а не тест.

### Когда останавливаться и спрашивать
- Архитектурная развилка с trade-off (а не техническая деталь) — НЕ угадывать. Записать варианты в Progress Log под заголовком `## NEEDS DECISION`, остановиться на этой задаче и перейти к следующей независимой.
- Этап, для которого в спеке нет раздела с требованиями (см. таблицу ниже) — НЕ придумывать требования. Собрать вопросы, вынести в `## NEEDS DECISION`, перейти дальше.
- Если тесты не проходят и причина не ясна за разумное время — зафиксируй что именно сломано; не коммить сломанное как готовое (допустим коммит с явной пометкой WIP).

### Завершение сессии
- Тесты зелёные → `git add`, conventional-commit, `git push origin chordpro-viewer`.
- Всегда дописывай запись в **начало** Progress Log: `### YYYY-MM-DD HH:MM UTC — <итог>` + что дальше + блокеры. Пушить лог даже если код заблокирован.
- Один заход = один осмысленный кусок (примерно один коммит). Не пытаться закрыть всё за раз, оставлять чистую точку остановки.

## Решение по идентификатору песни (закрыто, не пересматривать)

**Внешний идентификатор — integer `songs.id`.** Ранний черновик спеки требовал `slug`; решение от 2026-07-25 это отменило, спека `docs/song-viewer-spec.md` §7 обновлена и содержит обоснование. Поле `songs.slug` в схеме остаётся, но идентификатором не служит.

Миграцию `id` → `slug` **не делать ни на одном этапе**. Если встретишь в коде или комментариях следы обратного — это устаревшие комментарии (например в `types.ts`, `db.ts`, где написано, что id — «строка из имени файла»); их можно поправить текстом, но поведение не менять.

## Этапы 2–10

Перед реализацией любого этапа:
1. Прочитать **указанные для него** разделы спеки (не по номеру этапа).
2. Прочитать текущее состояние затронутого кода — не полагаться на описания из старых сессий, код мог измениться.
3. Расписать этап на коммиты/файлы/тесты прямо в этом файле (заменить строку чек-листа подробным под-списком, как сделано для этапа 1), закоммитить обновление плана **отдельным коммитом** от кода.
4. Только потом писать код.
