# Architecture Guide

> Auto-generated by /aif based on codebase analysis. Update when architecture decisions change.

## Pattern: Feature-Sliced Design (FSD)

**Decision:** Adopt FSD methodology with `app → features → shared` layer hierarchy.

**Rationale:** The project has two distinct feature domains (reading plan and Bible reader) that need clean separation. FSD enforces one-directional dependencies and co-locates feature logic.

**Rules:**
- `app/` imports from `features/` and `shared/`
- `features/` imports from `shared/` only — never from other features
- `shared/` has no imports from `features/` or `app/`
- Cross-feature communication goes through `app/` or shared state

## Pattern: Server/Client Component Split (Next.js App Router)

**Decision:** Use React Server Components as default; opt into client-side with `'use client'` only where needed.

**Rationale:** Reduces bundle size and enables server-side data access. Next.js 16 + React 19 React Compiler further optimizes client components.

**Rules:**
- Data fetching in API routes or server actions, not client components
- Components needing state, effects, or browser APIs get `'use client'`
- All event handlers and animations live in client components

## Pattern: API Route Proxy for Directus

**Decision:** All Directus SDK calls from the client go through a Next.js API proxy (`/api/directus/[...path]`), never directly.

**Rationale:**
- `DIRECTUS_ADMIN_TOKEN` must never be exposed to the browser
- Centralized point for auth injection, error handling, and request validation
- Allows rate-limiting and logging at the proxy layer

**Implementation:**
- Server-to-server: direct `@directus/sdk` calls with admin token
- Client-to-Directus: `fetch('/api/directus/...')` → proxy adds auth header

## Pattern: Typed API Client

**Decision:** All client-side API calls go through `apiClient` from `@/shared/services/api/client.ts`, with typed endpoint functions in `endpoints.ts`.

**Rationale:** Single place for auth headers, error normalization, base path handling. TypeScript types for all responses caught at compile time.

**Structure:**
```
shared/services/api/
├── client.ts         → apiClient.get/post/patch/delete + ApiClientError
├── endpoints.ts      → typed function per API endpoint group
└── graphql.ts        → GraphQL query helpers
```

## Pattern: Auth — Lucia + SQLite + Telegram

**Decision:** Lucia v3 handles session management; Telegram Bot handles user identity.

**Auth Flow:**
1. User opens Telegram → Telegram WebApp injects `initData`
2. Client POSTs `initData` to `/api/auth/telegram`
3. Server verifies HMAC-SHA256 signature with `TELEGRAM_BOT_TOKEN`
4. Server calls `findOrCreateUser()` → creates Directus user if new
5. Lucia creates session → sets httpOnly cookie
6. Middleware (`src/middleware.ts`) guards `/dashboard/*` routes

**Session Storage:** SQLite via `better-sqlite3` (local file, fast, zero-config)

## Pattern: Environment-Based Feature Flags

**Decision:** Feature toggles via `NEXT_PUBLIC_*` environment variables.

**Current flags:**
- `NEXT_PUBLIC_AI_ENABLE` — toggles AI chat ("Chat with Pastor")
- `NEXT_PUBLIC_BASE_PATH` — deployment base path

## Pattern: Standalone Deployment with Base Path

**Decision:** `output: 'standalone'` in `next.config.ts`, deployed behind nginx with base path `/app`.

**Implications:**
- `NEXT_PUBLIC_BASE_PATH=/app` must be set in production
- All client-side URL construction uses `getApiPath()` from `@/shared/utils/api`
- `assetPrefix` and `basePath` both set in next.config.ts

## Pattern: Directus as Primary CMS/Data Layer

**Decision:** Directus CMS serves all structured content: Bible reading plan, verse of the day, user profiles, chapters metadata.

**Usage:**
- Reading plan data → `directus_nbc_plans` collection
- Verse of the Day → Directus collection via Flows
- User data → Directus users collection, linked to Telegram IDs
- AI responses → triggered via Directus Flows → n8n

## Pattern: Shared Utils

**Decision:** Pure utility functions in `shared/utils/` with no React dependencies.

**Key utils:**
- `cn()` — Tailwind class merging (tailwind-merge)
- `getApiPath()` — URL construction with basePath
- `date.ts` — date formatting for calendar/week view
- `bible.ts` — book name/chapter normalization

## Anti-Patterns to Avoid

- ❌ Calling Directus directly from client components
- ❌ Importing between feature slices (plan ↔ reading)
- ❌ Putting business logic in page components (use hooks)
- ❌ Hardcoding API URLs without `getApiPath()`
- ❌ Storing session data in localStorage (use Lucia cookies)
- ❌ Fetching data in client components without loading/error states
