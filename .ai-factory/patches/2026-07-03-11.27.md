# Offline navigation shows bare "Offline" text instead of the app

**Date:** 2026-07-03 11:27
**Files:** src/sw/sw-source.ts, src/sw/sw-source.test.ts, src/shared/components/ui/OfflineIndicator.tsx (new), src/shared/components/ui/OfflineIndicator.test.tsx (new), src/app/layout.tsx
**Severity:** high

## Problem

User report: "теперь в оффлайн режиме я вижу текст Offline и не вижу больше ничего
хотя все загрузил, было бы здорово увидеть индикатор что оффлайн и при этом дальше
пользоваться приложением". Offline navigations to visited pages returned a bare
`Offline` 503 text response instead of the app, even though the user had already
downloaded Bible/songs/plan into IndexedDB (feature/offline-pwa, Tasks 21-30).

## Root Cause

Two independent bugs, both introduced while building the offline-PWA feature and
undetected because unit tests only covered the pure `routeStrategy` decision function,
never the actual fetch-handling logic embedded in the SW body string.

1. **SW never cached HTML.** The `network-first-html` fetch branch in
   `src/sw/sw-source.ts` fetched navigations but never called `cache.put()` on success
   — only the `cache-first-static` branch (for `_next/static/**`) wrote to a cache. So
   `caches.match(req)` in the offline fallback path always missed, and every offline
   navigation fell through to `new Response('Offline', { status: 503 })`, regardless of
   whether the page had been visited before. This directly contradicted the plan's own
   design intent ("офлайн доступны посещённые страницы") — the intent was implemented
   nowhere.

2. **`OfflineIndicator` computed the wrong initial state on SSR.** `useState(() =>
   typeof navigator !== 'undefined' && !navigator.onLine)` assumed `navigator` is only
   defined in the browser. In the Next.js/Node SSR runtime, `navigator` exists as a
   global stub without an `.onLine` property, so `!navigator.onLine` evaluated
   `!undefined` = `true` — the server rendered the offline banner unconditionally on
   every page load, confirmed via raw `curl` output containing `data-offline-indicator`
   even with a healthy network.

## Solution

1. Extracted the routing handlers into two pure(-ish), independently testable async
   functions — `handleStaticAsset` and `handleNavigation` — following the same
   `.toString()`-embedding pattern already used for `routeStrategy` (single source of
   truth, no duplicated plain-JS logic in the template string). `handleNavigation` now:
   - caches every successfully fetched HTML document under a dedicated
     `app-shell-html-v1` cache,
   - on fetch failure, returns the exact cached page if present,
   - if no exact match (page never visited while online), falls back to ANY other
     cached page — same SPA bundle, client-side router takes over — so the app boots
     instead of showing nothing,
   - only returns the bare `Offline` text if the HTML cache is completely empty (truly
     the first-ever offline visit with nothing cached).
2. Moved the `navigator.onLine` read out of `useState`'s lazy initializer and into
   `useEffect` (which never runs during SSR), eliminating the hydration-time false
   positive. Initial state is always `false` (assume online) until the client-side
   effect corrects it.
3. Added `OfflineIndicator` — a small, non-blocking, fixed-position banner (mounted in
   root `layout.tsx` next to `ServiceWorkerRegistrar`) driven by the standard
   `online`/`offline` window events, so users get visible feedback without the app
   being blocked.

## Prevention

- When a service worker's fetch-handling logic is embedded as a plain-JS string (no
  build step), extract every distinct strategy branch into its own named, exported,
  independently unit-testable function — not just the routing *decision* function.
  Fetch/cache side effects are exactly where bugs like "forgot to cache.put()" hide,
  and they're invisible to tests that only exercise the decision logic.
- Any client component that reads `navigator`/`window`/browser-only globals to compute
  **initial** `useState` value is a latent SSR bug in Next.js — those globals exist as
  partial/stub objects in the Node runtime and silently produce wrong values instead of
  throwing. Verify SSR output directly with `curl` (not just the hydrated browser DOM)
  for any component with such logic.
- When manually testing offline behavior via Chrome DevTools MCP: the "Offline" network
  condition preset blocks requests but does **not** flip `navigator.onLine` (that
  reflects real OS-level connectivity, a separate mechanism) — real request-layer
  behavior (SW caching/fallback) can be tested via the DevTools offline emulation, but
  `online`/`offline` DOM event-driven UI must be tested by dispatching the events
  manually (`window.dispatchEvent(new Event('offline'))`).
- Dev-mode Turbopack chunk requests can behave unreliably under simulated offline
  (missing content-hashing, HMR websocket dependency) — always do the final offline
  verification pass against a production build (`next build && next start`), not
  `next dev`.
