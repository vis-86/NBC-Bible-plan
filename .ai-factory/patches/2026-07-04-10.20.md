# Офлайн-навигация App Router: клиентские маршруты падали в 503-заглушку

**Date:** 2026-07-04 10:20
**Files:** src/shared/offline/appShell.ts (new), src/shared/components/layout/DashboardLayout.tsx, src/app/dashboard/song/page.tsx (new), src/app/dashboard/songs/[id]/page.tsx (deleted), src/features/songs/components/SongCard.tsx, src/middleware.ts, src/shared/offline/downloadManager.ts, src/sw/sw-source.ts (+ тесты)
**Severity:** high

## Problem

После деплоя офлайн: дашборд открывается, но переход в Библию/Песни/календарь даёт
`GET /app/dashboard/songs 503 (Offline)` и статичную заглушку «Эта страница ещё не
открывалась офлайн…». Диагностика на проде через консоль (`caches`, resource-timing)
показала: все boot-чанки дашборда в кеше (MISSING=0), то есть проблема НЕ в чанках, а
в доставке документа маршрута.

## Root Cause

Клиентская навигация App Router (`router.push`) офлайн делает **RSC-flight fetch**
(в SW он `passthrough`, `mode !== 'navigate'`) → сеть падает → Next откатывается на
**hard-навигацию документа** (`GET /dashboard/songs`, `mode = navigate`) →
`handleNavigation` ищет документ в HTML-кеше по точному URL → его там нет.

Документы в HTML-кеш кладут **только реальные навигации** (NetworkFirst при загрузке).
Внутри приложения переходы идут client push → документ маршрута НИКОГДА не кешируется.
Дашборд — единственное исключение, потому что это `start_url` (открывается реальной
навигацией). «Скачать всё» наполняет IndexedDB данными, но про документный/app-shell
слой не знает вообще. Итог: любой маршрут, куда ходят client push, офлайн → 503.

Динамические сегменты (`read/[book]/[chapter]`, `songs/[id]`) усугубляли: бесконечное
множество URL-документов, которые нельзя предкешировать по одному ключу.

## Solution

**1. Схлопнуть динамику в query (approach C).** Ридер → `/dashboard/read?book=&chapter=`,
деталь песни → `/dashboard/song?id=`. Search не меняет сегмент маршрута → один документ
обслуживает любые значения. В SW `handleNavigation` добавлен фолбэк
`cache.match(request, { ignoreSearch: true })`: один закешированный документ отдаётся
на любой query того же pathname. Безопасно (в отличие от подстановки чужого маршрута):
pathname тот же → RSC-payload того же маршрута, гидратация не уходит в reload-цикл;
book/chapter/id читаются клиентом из `location.search` + IDB. Старые URL редиректятся в
middleware.

**2. Прогрев app-shell документов в HTML-кеш** (`appShell.warmAppShell`): конечный
набор маршрутов (`/dashboard`, `/dashboard/read`, `/dashboard/songs`, `/dashboard/song`,
`/dashboard/calendar`, `/dashboard/settings`). Вызывается из `DashboardLayout` на
онлайн-старте (раз за сессию) → **само-лечится после каждого деплоя** (кладёт свежие
документы с новыми хешами чанков), и в конце «скачать всё». Жёсткий фильтр: кешируем
только `2xx` + `text/html` + не-redirect — иначе закешируем логин-редирект как документ
маршрута. Плюс `storage.persist()` на онлайн-старте — против выселения Cache Storage на
iOS (вероятная причина белого экрана при переоткрытии PWA офлайн).

## Prevention

- **Офлайн в App Router: client-навигация ≠ доступность документа.** Любой маршрут,
  куда ходят `router.push`, офлайн уйдёт в hard-nav и потребует ЗАКЕШИРОВАННЫЙ документ.
  Data-в-IDB недостаточно — нужен app-shell документ в HTML-кеше. При добавлении нового
  клиентского маршрута — добавить его в `APP_SHELL_ROUTES`.
- **Не держать данные в сегментах маршрута, если клиент читает их сам.** book/chapter/id
  → в search, а не в `[slug]`. Тогда набор app-shell маршрутов конечен и `ignoreSearch`
  обслуживает всё офлайн одним документом.
- **`ignoreSearch` безопасен только при одинаковом pathname** (тот же RSC-маршрут,
  параметры читаются клиентом). Для server-разного-по-query — нельзя.
- **Прогрев защищённых маршрутов — только в аутентифицированном контексте**, иначе
  закешируешь логин-страницу. Фильтровать redirect/не-html/не-2xx.
- **iOS выселяет несохранённый Cache Storage** — `storage.persist()` дёргать на старте,
  не только при явной загрузке.
- **Диагностика офлайн-PWA:** сравнивать закешированные документы/чанки против реально
  загруженных (`performance.getEntriesByType('resource')`), а не regex по HTML — во flight
  payload легко нахватать мусора и получить ложный «рассинхрон».
