# Офлайн: невозможно открыть песню, хотя всё скачано

**Date:** 2026-07-03 22:34
**Files:** src/features/songs/hooks/useSong.ts, src/features/songs/lib/offlineSongs.ts (new), src/features/songs/lib/offlineSongs.test.ts (new)
**Severity:** high

## Problem

Офлайн список песен открывался, но при тапе на песню страница просмотра падала
«Песня не найдена» — при том что пользователь заранее выполнил «скачать всё».

## Root Cause

Асимметрия read-путей между списком и деталью. Массовая загрузка (`downloadSongs`)
пишет полный контент каждой песни в отдельный IDB store `songs` (ключ = `Song.id`).
Список (`useSongs`) читается через общий `readThrough` + `apiCache` с IDB-фолбэком —
поэтому офлайн работал. А деталь (`useSong`) звала `songsApi.getSong(id)` напрямую
через `apiClient.get`, вообще без офлайн-фолбэка: офлайн `fetch` кидал ошибку →
`error` → «Песня не найдена». Скачанный контент лежал в IDB, но read-путь детали
туда никогда не заглядывал.

Классическая ошибка: офлайн-фолбэк добавили в один из read-хуков фичи и забыли про
второй, который пишет/читает в другой store.

## Solution

Добавлен feature-локальный офлайн read-through для одной песни
(`features/songs/lib/offlineSongs.ts`): `readSongThrough(id, fetcher)` — network-first,
при ошибке сети отдаёт песню из store `songs` по `String(id)`; при успехе пишет туда же
(теперь и просмотренная онлайн песня доступна офлайн без явного «скачать всё»).
`useSong` переведён с голого `songsApi.getSong` на `readSongThrough`. Ключ хранится
строкой — read принимает `string | number` и коэрсит через `String(id)`, т.к. `useSong`
получает id из route-params (string), а вызывать могут и числом.

Логика лежит в `features/songs` (не в `shared/offline`), чтобы не тянуть доменные типы
песен в shared-слой (FSD: features → shared, не наоборот).

## Prevention

- Для каждого офлайн-ресурса свести read-пути к ОДНОМУ read-through-хелперу. Если
  данные пишутся в свой store (не `apiCache`) — фолбэк должен читать именно тот store.
- Ревью-чек: при добавлении офлайн-фолбэка к списочному хуку сразу проверить парный
  detail-хук (и наоборот) — оба ли идут через один и тот же network-first+IDB слой.
- Тест-чек: для офлайн-фич покрывать сетевую ошибку (fetcher rejects) с заранее
  положенной в IDB записью — именно этот кейс и был не покрыт.
