# Офлайн: кнопки не работают — RSC-пейлоад ищется в precache по URL с `_rsc`, промах всегда

**Date:** 2026-07-10 14:58
**Files:** src/sw/sw.ts, src/sw/sw.test.ts, e2e/offline/offline-navigation.spec.ts, docs/offline-pwa.md
**Severity:** critical

## Problem

Офлайн на устройстве дашборд отрисовывался, но ни одна кнопка не работала: не
открыть Библию, главу по плану, профиль. Ошибок нет — клик просто ничего не делает.
Прямой ввод URL и перезагрузка страницы при этом работали.

## Root Cause

`respondToStaticAsset` искал ответ в precache по **точному URL запроса, включая query**:
`cache.match(requestUrl)`.

Клиентская навигация App Router (`router.push`) в режиме `output: 'export'` запрашивает
не документ, а RSC/flight-пейлоад: Next дописывает `.txt` к pathname и добавляет
cache-busting `_rsc=<hash>`, **уникальный для каждой навигации**. Итоговый URL —
`/app/dashboard/read.txt?book=john&chapter=3&_rsc=1a2b3c`. Ключ в precache пишется из
`out/` без query: `/app/dashboard/read.txt`. **Совпадение невозможно ни при каких
условиях** → SW всегда уходил в `fetch(req)` на сеть. Данные всё это время лежали в
прекеше — не совпадал только ключ поиска.

Почему симптом «мёртвая кнопка», а не ошибка — тот же корень, что в патче
`2026-07-05-08.55.md`: два режима офлайна ведут себя противоположно.

| Режим | `fetch` | Что делает Next | Итог |
|---|---|---|---|
| Авиарежим, Playwright `setOffline` | отклоняется мгновенно | `catch` → `doMpaNavigation` | hard-навигация → HTML из precache → **работает** |
| Реальный офлайн (мёртвая сота, Wi-Fi без аплинка) | **висит** | `catch` не срабатывает | fallback не наступает → **кнопка не делает ничего** |

Отсюда же и слепое пятно тестов: `offline-navigation.spec.ts` кликал по нижней навигации
и **проходил** — но лишь потому, что `setOffline(true)` отклоняет запрос мгновенно и
срабатывал MPA-фолбэк, маскируя баг. `cold-start-any-route.spec.ts` использует
`page.goto()` — это `mode === 'navigate'`, другая ветка (`respondToNavigation`), где query
уже игнорировался. Ни один спек не проверял, что офлайн-переход остаётся SPA.

## Solution

Чистая функция `precacheLookupKeys(requestUrl)` → `[точный URL, URL без query]` (при
отсутствии query — один ключ, лишний `cache.match` не нужен). `respondToStaticAsset`
перебирает ключи и возвращает первое попадание; сеть — только при промахе по всем.

Отдельная функция, а не `cache.match(url, { ignoreSearch: true })`: тестируется без
Cache API и не зависит от того, реализует ли мок опции `match`. Сигнатура
`PrecacheReader.match(key: string)` не менялась.

Логи `[SW][FIX]` (не голый `[FIX]` — весь остальной SW пишет `[SW]`): по какому ключу
попадание и был ли уход в сеть.

Проверено в реальном браузере на офлайн-SW (`chromium` + precache из `out/`):

| Запрос | до фикса | после |
|---|---|---|
| `dashboard/read.txt?book=…&_rsc=1a2b3c` | `Failed to fetch` | `200`, 12907 B, `text/plain` |
| `__next._tree.txt?_rsc=deadbeef` (segment-prefetch) | `Failed to fetch` | `200`, 1250 B |
| `dashboard/read.txt` (без query, контроль) | `200` | `200` |
| `nope-not-in-manifest.txt?_rsc=x` | `Failed to fetch` | `Failed to fetch` (сеть, верно) |

`content-type: text/plain` сохраняется → Next распознаёт ответ как flight и остаётся
на SPA-пути, а не сваливается в MPA.

## Prevention

- **Ключ прекеша и ключ запроса — разные вещи; сверяй их буквально.** Запись кладётся из
  файла (`out/…`), а читается по URL реального запроса. Любой cache-busting параметр
  (`_rsc`, `?v=`, `?t=`) делает точное совпадение невозможным. Ревью-чек: для каждого
  `cache.match(x)` спросить «под каким именно ключом это клали в `install`?».
- **Зелёный офлайн-тест ≠ рабочий офлайн.** `setOffline(true)` отклоняет fetch мгновенно
  и включает MPA-фолбэк Next, который маскирует промах SW. Реальный офлайн запрос
  **вешает**. Офлайн-тест обязан проверять не «контент отрисовался», а **что сеть вообще
  не понадобилась**.
- **Эмулировать зависание сети в Playwright нельзя:** `page.route`/`context.route` не
  перехватывают запросы, прошедшие через service worker (playwright#1090), а
  `serviceWorkers: 'block'` убирает предмет теста. Поэтому баг ловится через наблюдаемое
  следствие — произошёл ли MPA-фолбэк: маркер на `window` (переживает SPA, умирает при
  reload) + отсутствие console-ошибки `Failed to fetch RSC payload`.
- Для SW-слоя дешёвая и надёжная проверка — прямой `fetch()` из офлайн-страницы по
  URL-у, который делает Next, без прогона всего пользовательского сценария.
- **Остаточный риск (вне скоупа):** промах прекеша для `.txt` по-прежнему уходит в
  `fetch(req)` и в реальном офлайне повиснет. Все маршруты приложения прекеш-нуты, на
  кнопки это не влияет; закрытие класса целиком — таймаут на сетевой фолбэк в SW.
