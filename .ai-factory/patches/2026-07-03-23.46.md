# Офлайн после «скачать всё»: дашборд «Load failed» + Библия не открывается

**Date:** 2026-07-03 23:46
**Files:** src/shared/offline/downloadManager.ts, src/features/plan/contexts/PlanContext.tsx, src/app/dashboard/read/page.tsx (new), src/app/dashboard/read/[book]/[chapter]/page.tsx (deleted), src/middleware.ts, src/sw/sw-source.ts, src/app/dashboard/page.tsx, src/app/dashboard/calendar/page.tsx, src/features/plan/components/PlanView.tsx, src/shared/components/layout/BottomNavBar.tsx (+ тесты)
**Severity:** high

## Problem

Пользователь выполнил «скачать всё», закрыл и переоткрыл PWA офлайн. Два симптома:
1. Дашборд показывал «Load failed» вместо плана.
2. Библия открывала статичную заглушку «Эта страница ещё не открывалась офлайн…».

## Root Cause

Два независимых корня, оба — в доставке страниц/прогресса, не в контенте (текст глав
и песни лежали в IDB и читались через read-through фолбэки).

**Симптом 1 — прогресс читался fatal-путём.** `PlanContext.fetchPlan` делал два
`readThrough`: `plan:days` (прогревался в `downloadPlan`) и `plan:progress` (НЕ
прогревался). Офлайн read-through по непрогретому ключу пробрасывает ошибку сети; в
`fetchPlan` один `throw` из ветки прогресса уводил ВЕСЬ метод в `catch` →
`setError('Load failed')`, хотя `plan:days` в кеше есть. Прогресс — это обогащение
поверх дней, а не обязательные данные; его отсутствие ронять экран не должно.

**Симптом 2 — SW кеширует документы по ТОЧНОМУ URL и только для реально посещённых
страниц.** Ридер жил на динамическом маршруте `[book]/[chapter]` → бесконечное
множество URL-документов, которые нельзя предкешировать по одному ключу. «Скачать всё»
наполняет IDB, но ничего не делает для документного/app-shell слоя. Клиентская
навигация App Router (`router.push`) → RSC-flight фетч (passthrough в SW) → офлайн
падает → Next hard-reload → `handleNavigation` не находит точного URL в HTML-кеше →
статичная заглушка. Подставить HTML другого маршрута нельзя — вшитый RSC-payload
другого URL уводит App Router в цикл hard-reload (задокументировано в SW).

## Solution

**Часть 1 (низкий риск):**
- `downloadPlan()` дополнительно прогревает `plan:progress` (`progressApi.getProgress`)
  тем же логическим ключом, что читает `PlanContext` — закрывает кейс «скачал всё, ни
  разу не открыв план онлайн».
- `fetchPlan` читает прогресс в отдельном try/catch: при неудаче логирует `[FIX]`
  warning и рендерит план БЕЗ снапшота прогресса (outbox-overlay всё равно накрывает
  офлайн-отметки). `setError` больше не срабатывает от недоступного прогресса.

**Часть 2 — approach C (схлопнуть динамику в один маршрут):**
- Ридер переведён с сегментов `[book]/[chapter]` на ОДИН клиентский маршрут
  `/dashboard/read` с `book`/`chapter` в search-параметрах. Search не меняет сегмент
  маршрута → один документ/RSC-shell обслуживает любую главу; бесконечность
  динамических URL устранена. `useSearchParams` обёрнут в `<Suspense>`.
- `handleNavigation` в SW: при промахе точного совпадения — фолбэк
  `cache.match(request, { ignoreSearch: true })`. Один закешированный документ
  `/dashboard/read?...` обслуживает любую другую главу офлайн. БЕЗОПАСНО (в отличие от
  подстановки чужого маршрута): pathname тот же → RSC-payload того же маршрута, без
  reload-цикла; книга/глава читаются клиентом из `location.search` + IDB. ignoreSearch
  не может выдать документ другого pathname.
- `downloadManager.warmReaderShell()` прогревает документ ридера в HTML-кеш при
  «скачать всё» — для кейса «ни разу не открывал ридер онлайн».
- `middleware.ts` редиректит старые `/dashboard/read/<book>/<chapter>` → новый формат
  (deep-link/закладки). Все `router.push` call-site'ы (dashboard, calendar, PlanView,
  BottomNavBar) переведены на `?book=&chapter=`.

## Prevention

- **Обязательные vs обогащающие данные в одном fetch.** Если экран строится из
  нескольких источников, «обогащающие» (прогресс, счётчики) читать в отдельном
  try/catch — их сбой не должен ронять весь экран. Один общий `try` вокруг всего =
  самый хрупкий источник диктует доступность экрана.
- **Прогрев кеша должен покрывать ВСЕ ключи, что читает экран.** При добавлении
  read-through к экрану сразу проверять, что download/warm-up прогревает каждый его
  логический ключ (тот же класс бага, что и с песнями в патче 2026-07-03-22.34).
- **Офлайн-навигация в App Router: избегать динамических сегментов для данных,
  различимых на клиенте.** Параметры, которые клиент и так читает из URL (book,
  chapter, id), держать в search, а не в сегментах маршрута — тогда один
  закешированный документ + `ignoreSearch` обслуживает всё офлайн. Динамический
  сегмент = отдельный документ на каждое значение = не кешируется офлайн.
- **Ревью-чек SW:** `ignoreSearch` безопасен только когда разные query при одинаковом
  pathname рендерят один и тот же RSC-маршрут (client-side чтение параметров). Для
  server-разных страниц по query — нельзя.
