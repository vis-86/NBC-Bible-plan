# Офлайн «не работает»: пустой экран → вечная загрузка — network-first без таймаутов

**Date:** 2026-07-05 08:55
**Files:** src/shared/offline/networkTimeout.ts (new), src/shared/offline/readThrough.ts, src/shared/offline/db.ts, src/sw/sw-source.ts, src/components/AuthProvider.tsx, src/features/songs/lib/offlineSongs.ts, src/features/reading/hooks/useBibleText.ts (+ тесты)
**Severity:** high

## Problem

Пользователь в офлайне видел пустой экран, через длительное время — вечный
FullScreenLoader. При этом на десктопе с DevTools → Offline и в авиарежиме всё
работало идеально (воспроизведено на живом проде: reload, холодный старт, навигация —
всё отдавалось из кешей мгновенно и корректно).

## Root Cause

**Два режима «офлайна» ведут себя противоположно, а код был написан только под один.**
В авиарежиме/DevTools `fetch` отклоняется мгновенно → все catch-фолбэки (SW HTML-кеш,
last-known-user, IDB read-through) срабатывают сразу. В реальном «офлайне» (мёртвая
сота, Wi-Fi без аплинка, captive portal, VPN-дыра) сеть НЕ отказывает — запросы
**висят минутами** до браузерного таймаута. Ни один network-first путь не имел
таймаута, поэтому фолбэк просто не наступал:

- SW `handleNavigation` ждал fetch документа → пустой экран до таймаута браузера;
- `AuthProvider.checkSession` ждал `/api/auth/session` → `authLoading` не снимался →
  вечный FullScreenLoader (дальше него приложение не пускало);
- `readThrough`/`readSongThrough`/`useBibleText` ждали свои fetch → данные из IDB
  не отдавались.

Каждый слой ждал полный браузерный таймаут ПОСЛЕДОВАТЕЛЬНО — суммарно минуты.

Сопутствующий баг (найден при чтении того же кода): `handleNavigation` кешировал
любой `res.ok` ответ, включая **redirected** — навигация на `/dashboard` с истёкшей
сессией отдаёт редирект на логин-страницу с `ok === true`, и она кешировалась под
ключом `/dashboard`: офлайн приложение вечно открывалось бы логин-страницей.

Второй сопутствующий: iOS WebKit иногда вечно виснет на `indexedDB.open()` после
холодного старта PWA — `getDB()` без таймаута замораживал бы все офлайн-пути даже
в авиарежиме (caller'ы обрабатывают reject, но не бесконечный pending).

## Solution

Единый паттерн «race с таймаутом» (`shared/offline/networkTimeout.ts`,
`raceWithTimeout` + `NetworkTimeoutError`, дефолт 6s): по таймауту пробуем фолбэк
(кеш/IDB/last-known-user); **если фолбэка нет — дожидаемся исходный запрос**
(медленная сеть лучше ошибки, когда отдать нечего). Применён во всех network-first
путях: `readThrough`, `readSongThrough`, `useBibleText`, `AuthProvider.checkSession`.
В SW — инлайн-race (тело сериализуется, импорты недоступны), `NAV_TIMEOUT_MS = 4000`
передаётся параметром (не module-конста — минификация ломает свободные ссылки).
`getDB()` — race открытия с 5s + сброс singleton для ретрая. Redirected-ответы в SW
больше не кешируются. Поздние reject затираются `network.catch(() => {})` — иначе
unhandled rejection после ухода в фолбэк.

## Prevention

- **Офлайн ≠ отказ сети.** Любой network-first путь обязан иметь таймаут: реальный
  офлайн ВЕШАЕТ запросы, а не роняет их. Тестировать офлайн только через
  DevTools → Offline недостаточно — обязателен кейс «fetcher никогда не резолвится».
- Ревью-чек: у каждого `await fetch(...)` перед фолбэком спросить «что будет, если
  этот промис не резолвится 2 минуты?».
- Паттерн фолбэка по таймауту: есть кеш → отдать кеш; кеша нет → ждать сеть дальше
  (не превращать медленную сеть в ошибку).
- SW `cache.put` для навигаций — только `res.ok && !res.redirected`: redirect на
  логин под ключом маршрута = офлайн-приложение навсегда подменяется логин-страницей.
- Тест-чек: для каждого read-through — тест «fetcher hangs (new Promise(() => {})) +
  запись в кеше» и «fetcher hangs + кеш пуст → дожидается сеть».
