# Offline navigation shows white "Offline" screen / infinite reload loop for any never-hard-visited route

**Date:** 2026-07-03 16:03
**Files:** src/sw/sw-source.ts, src/sw/sw-source.test.ts, src/shared/components/ui/OfflineIndicator.tsx
**Severity:** critical

## Problem

Offline, tapping any bottom-nav item other than the current page produced a blank
white screen with the literal text "Offline". Reported as: navigation is unusable
offline no matter which menu item is tapped.

## Root Cause

Two independent bugs stacked in `src/sw/sw-source.ts`:

1. `routeStrategy()` classified *any* same-origin non-static/non-api GET as
   `network-first-html` — including Next.js App Router's RSC/flight fetches issued
   by client-side `router.push()` (mode `cors`/`same-origin`, not `navigate`). These
   carry a cache-busting `_rsc=<hash>` query param that never repeats. Offline, the
   RSC fetch failed inside `handleNavigation`, found no cache match, and (once the
   HTML cache held nothing usable) fell through to `new Response('Offline', {status:
   503})` — the exact bare-text screen reported. Next.js then treated the malformed
   (non-flight) response as a failed navigation and forced a hard MPA reload, which
   hit the SW again with the same problem.

2. Once RSC fetches were correctly excluded (fix #1) and hard-navigation fallback
   started firing directly, a second latent bug surfaced: `handleNavigation`'s
   catch-all fallback served *any other* cached page's HTML as a stand-in "app
   shell" for a route with no exact cache match ("тот же бандл, клиентский роутинг
   подхватит" per the original code comment). This assumption is wrong for
   Next.js App Router: the served document embeds the RSC/flight payload for the
   route it was actually fetched for. Serving `/dashboard`'s cached document in
   response to a `/dashboard/songs` request causes React hydration to detect the
   route mismatch and Next.js to retry via another hard reload — reproduced live as
   an infinite reload loop (confirmed via repeating console entries: React DevTools
   banner + failed manifest/icon fetches + HMR websocket reconnect, over and over,
   with the error count climbing with no further input).

Neither path had test coverage for RSC-shaped requests or for the cross-route
fallback case, so both went unnoticed until manual offline reproduction in a real
browser (Playwright, `context.setOffline(true)`).

## Solution

- `routeStrategy(pathname, method, sameOrigin, mode)` gained a `mode` parameter;
  only `mode === 'navigate'` (a real document navigation) is routed to
  `network-first-html`. Everything else (RSC/flight fetches, prefetches) is
  `passthrough` — the SW no longer touches them, so a failed RSC fetch surfaces as
  a normal rejected promise and lets Next's own `doMpaNavigation` fallback fire
  cleanly instead of being fed a mismatched/corrupt response.
- `handleNavigation`'s no-exact-match branch no longer substitutes another page's
  cached HTML. It now returns a small, static, self-contained `OFFLINE_FALLBACK_HTML`
  (no Next.js runtime references) with `503`/`Offline` status — informing the user
  the page was never opened offline, instead of looping or showing a bare 503 with
  no markup.
- Updated `OfflineIndicator.tsx`'s doc comment (it referenced the now-removed
  cross-route fallback behavior).
- Live-verified via Playwright with real CDP offline emulation against a logged-in
  session: before the fix, clicking a bottom-nav item offline produced either the
  bare "Offline" text or (after fix #1 alone) an infinite reload loop; after both
  fixes, navigating to a never-visited route offline renders the real page
  (header, search, and — since it had been read online earlier in the session —
  actual data from the IndexedDB read-through layer), with no loop and no blank
  screen. Exact-match cached routes (e.g. returning to a page hard-loaded earlier)
  continued to work as before.

## Prevention

- When a service worker's fetch handler branches on request shape, always check
  `request.mode` (`navigate` vs `cors`/`same-origin`/`no-cors`) before assuming a
  same-origin GET is a document navigation — frameworks with client-side data
  fetching (RSC, GraphQL persisted queries, etc.) route plain `fetch()` calls
  through the exact same origin/path space as real page loads.
- Don't assume "any cached HTML document" is an interchangeable app-shell fallback
  for frameworks that embed route-specific payload in the document (RSC/Islands/
  hydration frameworks in general) — verify cross-route substitution against the
  actual framework's hydration behavior, not just by inspection of the SW code.
  A unit test with a `Request` object is not sufic ient network in the loop; the
  only test that caught bug #2 was a real offline browser reproduction that let
  the reload loop actually run.
- For offline-first SW work in this codebase specifically, add a live
  Playwright-with-CDP-offline check (`context.setOffline(true)`, click through
  bottom-nav items, watch console-error count over time) as a normal part of
  verifying any SW routing change — a stuck/looping page won't show up in `vitest`
  unit tests alone.
