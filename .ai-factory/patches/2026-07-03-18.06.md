# SW crashes in production with "Can't find variable: y" — free-variable reference in a `.toString()`-serialized function

**Date:** 2026-07-03 18:06
**Files:** src/sw/sw-source.ts, src/sw/sw-source.test.ts
**Severity:** critical

## Problem

After deploying the previous offline-navigation fix (patch 2026-07-03-16.03), a real
device in airplane mode hit: `FetchEvent.respondWith received an error:
ReferenceError: Can't find variable: y`. Every intercepted navigation failed outright.

## Root Cause

`src/sw/sw-source.ts` builds the actual service worker script at request time by
calling `.toString()` on `routeStrategy`, `handleStaticAsset`, and `handleNavigation`
and splicing the resulting source text into a template literal (`buildSwBody()`,
`src/app/sw.js/route.ts`). The file's own doc comments say these functions must be
"pure — must not reference anything outside their arguments", precisely because
their *source text*, not a live closure, ends up embedded in the generated script.

My previous fix added `return new Response(OFFLINE_FALLBACK_HTML, ...)` inside
`handleNavigation`, reading `OFFLINE_FALLBACK_HTML` as a free variable from module
scope — violating that rule. It worked in `next dev` (unminified) and even in a
first local production-build smoke check I didn't run deeply enough at the time.
In the real Next.js production bundle, the server-side module containing
`sw-source.ts` gets minified, so the *compiled* `handleNavigation.toString()`
referenced the constant under its minified name (observed later as a single-letter
identifier). Meanwhile `buildSwBody()` re-declares the constant under its
**original, unminified** name (`const OFFLINE_FALLBACK_HTML = ${JSON.stringify(...)}`)
in the generated SW text. The minified function body and the re-declared constant
no longer agreed on a name — `ReferenceError: Can't find variable: y` at the exact
moment `handleNavigation`'s catch branch tried to build the offline fallback
response, i.e. on literally every offline navigation.

Unit tests didn't catch this because Vitest runs the TypeScript source directly,
never through Next's production minifier — the exact same reason the *first*
patch's app-router reload-loop bug had gone unnoticed too (this class of "only
breaks once actually built/bundled/run offline" bug does not show up in unit tests
or `next dev` at all).

## Solution

- `handleNavigation` now takes `offlineFallbackHtml` as its 4th parameter instead
  of reading `OFFLINE_FALLBACK_HTML` from module scope — restoring the "only
  references its own arguments" invariant that makes `.toString()` serialization
  safe under minification.
- `buildSwBody()`'s call site passes `OFFLINE_FALLBACK_HTML` (available there under
  its real name, since that code is authored directly in the template literal, not
  serialized via `.toString()`).
- Added a regression test (`sw-source.test.ts`) that asserts none of the three
  serialized functions' `.toString()` output contains any module-level constant
  name (`SW_DISABLED`, `STATIC_CACHE_NAME`, `HTML_CACHE_NAME`,
  `OFFLINE_FALLBACK_HTML`) as a bare identifier — a cheap, permanent guard against
  reintroducing a free-variable reference in any of these functions.
- Verified against a real `next build` + `next start` production bundle (not just
  `next dev`): inspected the actual minified `/app/sw.js` output directly — confirmed
  `handleNavigation`'s minified parameter (`r`) is used consistently as the local
  arg, not a dangling free reference — then drove a real offline navigation
  (Playwright + CDP `setOffline(true)`) against that production build and confirmed
  no `ReferenceError`, real dashboard content rendered from the offline
  IndexedDB/last-known-user fallback path, and the `OFFLINE_FALLBACK_HTML` page
  rendered correctly for a never-visited route.

## Prevention

- Any function serialized via `.toString()` for embedding in a generated
  script (service workers, worker threads, `eval`-based codegen, etc.) must be
  verified against the **actual production, minified build** — `next dev` and
  Vitest both skip minification and will never catch this class of bug.
- Enforce the "pure, args-only" contract for such functions with an automated
  check (now in place: a test asserting the serialized source contains none of the
  module's own constant names) rather than relying on a doc comment alone —
  the doc comment already stated the rule correctly and was still violated.
- When touching `src/sw/sw-source.ts` specifically, the checklist going forward is:
  unit tests → `next build && next start` → inspect the real generated `/app/sw.js`
  output → drive a real offline navigation against that production server before
  calling an SW fix done.
