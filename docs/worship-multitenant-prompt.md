# Промпт: пространства музыкальных команд (мультитенантность)

> Скопировать в новую сессию в `~/Projects/nbc/bible-plan` и передать в `/aif-plan`.
> Решения приняты 2026-10-09 и пересмотрены 2026-11-02 в обсуждении с Игорем:
> вместо отдельного инстанса — общая БД, NBC — команда №1 (вариант A).

---

## Контекст

Другие церкви просят дать им раздел «Песни» для своих музыкальных команд. План чтения
Библии им не нужен. В будущем публичные песни любой церкви попадают в общий каталог,
и любая другая церковь может скопировать их себе.

Решение 2026-10-09 предполагало отдельный инстанс (свой Directus и своя БД) и отсутствие
общего каталога. Требование каталога это решение отменило:

- каталог — это выборка `songs` с `visibility = 'public'` по всем командам. В одной БД это
  один запрос, в двух — синхронизация между инстансами;
- основной контент — песни NBC (98 штук на 2026-11-02, все `public`). В отдельном инстансе
  их в каталоге нет без переноса между базами;
- изоляцию между командами писать в любом случае: в отдельном инстансе тоже 3–5 церквей.
  Отдельная БД ограждала от ошибки фильтра только NBC, а стоила второго Directus
  (300–500 МБ RAM, бэкапы, каждое изменение схемы песен — дважды).

Отдельный бэкенд на Spring/Quarkus отклонён ещё 2026-10-09: реальный гейт доступа уже живёт
в Hono BFF (Directus вызывается админ-токеном после `requireSongWrite` /
`requireSetlistWrite`, см. CLAUDE.md, «Роли доступа»).

## Масштаб

- 3–5 знакомых церквей. Саморегистрации нет: люди пишут Игорю лично.
- Вход только по инвайт-ссылке.
- Каталог — фаза 3, но модель данных под него (общая БД, `origin_song`) закладывается сразу.

## Архитектура

- **Данные:** один Directus, одна БД, один BFF. Данные разделены по команде (`team`).
  NBC — команда №1; для пользователей NBC ничего не меняется.
- **Витрины:** два статических билда из одной кодовой базы, оба ходят в один BFF.
  - `out/` — как сейчас: NBC, все модули, текущий домен.
  - `out-worship/` (`APP_MODE=worship`) — только песни и сеты, нейтральный бренд, свой домен.
    Скрыты Библия, планы чтения, Telegram-уведомления и привязка Telegram.
  - Почему билд, а не флаг в рантайме: манифест PWA (имя, иконки) и лендинг собираются при
    сборке — другие церкви не должны ставить себе приложение «НБЦ Библия».
  - Сборка идёт на сервере (`deploy.sh`) — второй `next build` удлиняет деплой; проверить,
    хватает ли RAM на сборку, второго Directus при этом нет.
- Модули по командам в рантайме не нужны: какие модули видны, решает витрина.

## Модель данных

```
teams            id, name, slug
team_members     team, user                  ← один пользователь = одна команда
songs            + team (required), + origin_song (M2O songs, nullable)
setlists         + team (required)
invites          + team, + role              ← расширить существующий src/lib/invite.ts
```

- `setlist_items` и `song_user_state` поля `team` не получают: до них добираются через сет
  и песню, которые уже отфильтрованы по команде. Проверка принадлежности — в BFF на записи
  (см. «Изоляция»).
- `songs.slug` и `songs.sort` остаются глобальными. Составной уникальный индекс Directus не
  умеет (уже упирались в `song_user_state`), а в URL slug не используется (маршруты — по `id`).
  `nextFreeSlug` и так разводит коллизии суффиксом; внутри команды `sort` — монотонная
  последовательность с пропусками, порядку списка это не мешает.
- **Один пользователь = одна команда** (компромисс ради простоты: в IDB нет пересечений
  между командами, в UI нет выбора команды). `team_members` позволит снять ограничение
  без переноса данных.

## Роли

- Источник роли не меняется: Directus-роль → `AppRole` через `resolveAppRole`
  (`src/lib/app-roles.ts`). Добавляется `team_admin`: управление участниками и инвайтами
  своей команды плюс права `musician_editor`.
- Итог: `reader` (просмотр), `musician` (CRUD сетлистов), `musician_editor` (плюс песни),
  `team_admin` (плюс участники). Параллельной системы ролей нет, роли пользователей NBC
  не мигрируют.
- Пока пользователь состоит в одной команде, глобальная Directus-роль по факту и есть роль
  в команде. При снятии ограничения «одна команда» роль переезжает в `team_members`.
- Роль читается на каждый запрос (`GET /api/user/role`), в iron-session не кэшируется.
- Directus-роли пользователей после изменения прав (см. «Второй рубеж») — только метки
  для `resolveAppRole`, доступа к данным команд они не дают.

## Изоляция команд — главный риск

BFF ходит в Directus админ-токеном, поэтому один забытый фильтр открывает данные другой
церкви, в том числе NBC.

### Правила
- `team` берётся **только из членства по сессии** (`directus_id` → `team_members`), никогда
  из тела запроса, query или URL.
- Весь доступ к `songs` / `setlists` / `setlist_items` / `song_user_state` — через один
  хелпер, который сам подставляет фильтр по команде. Статический тест в духе
  `runtime-closure.test.ts`: в `server/src/routes` и `features/*/services` нет прямых
  `readItems`/`createItem`/`updateItem`/`deleteItem` к этим коллекциям мимо хелпера.
- Тест на **каждый** роут: пользователь команды A обращается к ресурсу команды B → 404
  (не 403).
- В сет можно добавить только песню своей команды: `setlist_items.song` проверяется на
  записи. Иначе через сет утечёт чужая песня.
- Пометки (`song_user_state`) пишутся только к песне, видимой пользователю.

### Что меняется в коде
- **`server/src/routes/sync.ts`:** кеш манифеста — одна общая запись на 60 с; ключом
  кеша становится команда.
- **`src/components/AuthProvider.tsx`:** при входе другого пользователя на том же
  устройстве данные прежнего (песни, сеты, `apiCache`, пометки, очередь outbox) удаляются
  из IDB до того, как экраны прочитают кеш. Скачанное Писание остаётся.

### Второй рубеж (Directus)
- Доступ к коллекциям команд (`songs`, `setlists`, `setlist_items`) — только у BFF
  (админ-токен). Пользовательские политики (`custom`, `setlist_editor`) прав на них не
  имеют — как уже сделано для `songs`. Права на `setlists`/`setlist_items` снимаются
  отдельным шагом миграции (см. «Миграция NBC»).
- Пользовательские политики не дают чтения чужих строк и в общих коллекциях
  (`reading`, `telegram_user_mapping`): либо фильтр по владельцу, либо без прав —
  приложение работает с ними через BFF.
- `song_user_state` с фильтром `user_id = $CURRENT_USER` можно оставить.
- Прокси `/api/directus/*` ходит под учёткой пользователя: после снятия прав он к данным
  команд не пускает. В worship-витрине клиент его не использует. GraphQL-роут нужен только
  для прогресса плана (outbox) — в worship-витрине выключить.
- `mcp_agent` (MCP Игоря) видит данные всех команд — осознанно, это инструмент админа.

## Видимость и каталог

- `songs.visibility` уже есть: `members` — только своя команда, `public` — гостевая ссылка
  `/s?id=` **и** каталог (фаза 3). Для песен новых команд по умолчанию `members`:
  публикация — осознанное действие `musician_editor`/`team_admin` над конкретной песней
  (авторские права, CCLI).
- `GET /api/public/songs/:id` перебирается по целым `id` — допустимо: `public` и так означает
  «видна всем церквям». Прежняя идея `share_token` снята: она не нужна при каталоге.
- Если окажется, что делиться ссылкой хотят, а отдавать в каталог нет, — третий уровень
  видимости. Не сейчас.

### Каталог (фаза 3)
- Экран каталога: поиск по `public`-песням всех команд с названием команды-источника.
- **Копия — это форк, а не ссылка.** `POST /api/songs/:id/copy` под `requireSongWrite`:
  исходная песня должна быть `public`, команда назначения — из сессии. Создаётся новая
  песня своей команды с копией контента, `origin_song = id`, `visibility = members`.
  Почему форк:
  - команды правят аккорды и тональность под себя;
  - ink-пометки привязаны к хэшу строки — правка оригинала чужой командой их сломала бы;
  - удаление оригинала не должно отнимать песню у других;
  - офлайн и дельта-синк остаются внутри команды, каталог в IDB не попадает.
- `origin_song` даёт метку «уже у вас» в каталоге (повторно не копировать); «оригинал
  обновлён» — позже, если попросят.
- Дубли одной песни от разных команд при 3–5 церквях допустимы; группировку не делать.
- **Осознанное исключение из offline-first (согласовано 2026-11-02):** каталог работает
  только онлайн, с явным UI «нужен интернет». Скопированная песня дальше офлайн, как
  любая своя: после копирования обновить IDB и список, как после записи в редакторе (M9).

## Миграция NBC (фаза 1, прод)

1. Бэкап БД.
2. Коллекция `teams`, команда `nbc`; `team_members` для всех пользователей NBC.
3. Поля `songs.team`, `songs.origin_song`, `setlists.team` — nullable.
4. Backfill: всем песням и сетам `team = nbc`.
5. Деплой BFF с фильтром по команде (и чисткой IDB при выходе).
6. `team` → NOT NULL.
7. Снять права с пользовательских политик (см. «Второй рубеж»).

Каждый шаг обратим до шага 6; после деплоя — полный smoke критического пути NBC (вход,
песни, сеты, пометки, офлайн), а не только `GET 200`.

## Флоу команд (фаза 2)

1. **Игорь** запускает `scripts/create-team.ts "Церковь X"`: создаётся команда и инвайт
   для её первого `team_admin`. Админ-панель не пишем.
2. **`team_admin`** создаёт инвайт-ссылки для музыкантов с ролью, удаляет участников.
3. **Музыкант** переходит по ссылке, задаёт логин и пароль и попадает в команду из инвайта.
4. **Забытый пароль:** `team_admin` выдаёт reset-инвайт (`invite.kind === 'reset'` уже есть,
   `POST /auth/activate` в `server/src/routes/auth.ts`).

## Персональные данные

- Сохраняется инвариант: без email/телефона/ФИО, синтетический email `{login}@<домен>` с
  реальным TLD (Directus v11 отклоняет `.test`, `.invalid`, `@local`).
- Привязку `tg_id` в worship-витрине выключить.

## Фазы

1. **Основа:** команды, изоляция, второй рубеж, NBC — команда №1. Видимых изменений нет.
2. **Витрина:** `APP_MODE=worship`, домен, `create-team.ts`, инвайты с командой и ролью,
   `team_admin`.
3. **Каталог:** экран и копирование.

## Не делать

- Саморегистрацию команд, биллинг, админ-панель.
- Живую связь копии с оригиналом (синхронизацию правок оригинала в копии).
- Модерацию и группировку каталога.
- Модули по командам в рантайме — модули задаёт витрина.

## Открытые вопросы

- **Песни NBC в каталоге.** Все 98 сейчас `public` (гостевая ссылка). С каталогом это ещё
  и «любая церковь копирует к себе». Согласна ли церковь? Если нет — до запуска каталога
  перевести их в `members` или развести «ссылку» и «каталог» на разные уровни.
- **Бренд и домен витрины.** Если другим церквям нормально пользоваться приложением под
  брендом НБЦ, хватит одного билда и модулей по команде в рантайме (минус одна сборка в
  деплое, плюс поле `teams.modules`). Домен для worship-витрины не выбран.
- **Перенос песен для новой команды:** копирование из каталога закрывает часть случаев;
  импорт ChordPro-файлов (переиспользовать `scripts/songs-import/`) или только ручной ввод.
