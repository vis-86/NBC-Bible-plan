## 1. Зачем переписываем

Текущий вьювер (~1.8k LOC) построен вокруг **фиксированной виртуальной страницы A4 800×1131 px**,
которая масштабируется под экран. Отсюда каскадом растёт вся сложность:

| Что есть сейчас | Почему существует | Судьба |
| :--- | :--- | :--- |
| `columnHeightCalculator.ts` (504) | ручной расчёт, что влезет в колонку фиксированной высоты | **удалить** → CSS multicol |
| `a4Fit.ts` + `useZoomPan` | вписать фикс-страницу в экран | **удалить** → reflow |
| `ChordProBlockSvg.tsx` (657) | `canvas.measureText` + SVG для позиционирования аккордов | **удалить** → inline-block |
| `mergeShortLines.ts`, `songLayoutEngine.ts` | компенсация отсутствия reflow | **удалить** |
| persist зума | компенсация отсутствия управления размером шрифта | **удалить** |

Принцип нового движка (подтверждён тем, как устроены OnSong R2 и WorshipTools Charts):
**музыкант управляет режимом отображения и размером шрифта, а не зумом.**
Зум — костыль там, где нет нормального reflow. Reflow будет.

### Целевые числа

- Ядро рендера: **≤ 400 LOC** (`SongSheet` + токенизатор + CSS).
- Ноль измерений DOM в рендер-пути. Ноль `canvas`, ноль `ResizeObserver` для раскладки.
- Один рендер-путь на экран, печать и PDF-экспорт.

## 2. Формат данных: что реально в корпусе

Проверено на 97 файлах `data/songs/*.chordpro` (июль 2026).

**Используемые директивы — и только они:**

| Директива | Кол-во | Назначение |
| :--- | ---: | :--- |
| `{comment: …}` | 914 | **метка секции** («Куплет 1», «Припев», «Вступление», «Модуляция») |
| `{key: …}` | 98 | тональность |
| `{title: …}` | 97 | название |
| `{tempo: …}` | 85 | темп |
| `{time: …}` | 81 | размер |
| `{subtitle: …}` | 62 | оригинал/аранжировка |
| `{artist:}` / `{author:}` | 13 | автор |

Директив окружения (`{soc}`/`{eoc}`/`{sov}`), `{column_break}`, `{define}` в корпусе **нет**.
Секция = блок строк от одного `{comment:}` до следующего (или до конца).

**Токены в квадратных скобках — не всегда аккорды:**

| Вид | Пример | Как рендерить |
| :--- | :--- | :--- |
| аккорд | `[G]`, `[C/G]`, `[F#sus4]`, `[Bm7]` | обычный аккорд, транспонируется |
| тактовая черта | `[\|]` | вертикальная черта, **не** транспонируется, не участвует в поиске |
| цепочка | `[E-B/D#-E/D]` | сплошной блок; транспонировать каждый элемент через `-` |
| текстовая пометка | `[(пауза)]`, `[(capella)]` | курсив, не транспонируется |
| битые данные | `[C#mсть.]` | fallback: рендерим как есть, не падаем |

**Строки бывают трёх видов:**

1. Текст с аккордами — `"М[G]уж скорбей” так н[C]азван Т[D]от,` (аккорд может стоять **внутри слова**).
2. Только аккорды — `[G][\|][C/G][\|][G][\|][C/G][\|]` (до 42 таких строк в одной песне).
3. Только текст — без токенов.

**Экстремумы корпуса (тест-кейсы):**

- самая длинная песня — `64-его-слава-благо-мне.chordpro` (101 строка);
- самая плотная строка — `45-святая-ночь.chordpro`, 110 символов с 7 токенами вперемешку с `[|]`;
- больше всего аккордовых строк — `66-на-кресте-совершилось-всё.chordpro` (42).

## 3. Модель рендера

### 3.1 Токенизация (чистая функция, без DOM)

```ts
type Chord = { kind: 'chord'; text: string };      // [G], [C/G], [E-B/D#-E/D]
type Bar   = { kind: 'bar' };                       // [|]
type Note  = { kind: 'note'; text: string };        // [(пауза)]
type Marker = Chord | Bar | Note;

/** Пара «маркер + прилипший к нему кусок текста». */
type Token = { marker: Marker | null; lyric: string };

type Line =
  | { kind: 'tokens'; tokens: Token[] }   // текст и/или аккорды
  | { kind: 'blank' };

type Section = { label: string | null; lines: Line[] };

function parseSong(content: string): { meta: Metadata; sections: Section[] };
```

Правила токенизации:

- Текст **до первого** маркера в строке → `{ marker: null, lyric: '...' }`.
- Пробелы сохраняются в `lyric` как есть (`white-space: pre-wrap` на токене).
- Аккордовая строка = все токены имеют пустой `lyric` → флаг `chordsOnly` на строке, отдельный стиль.
- Классификация маркера: `|` → Bar; `^\(.*\)$` → Note; иначе Chord.
- Парсер **не валидирует** аккорды — неизвестный текст рендерится как есть.

### 3.2 DOM: аккорд над слогом без измерений

```html
<span class="tok">
  <span class="chord">Am</span><span class="lyr">сло</span>
</span>
```

```css
.tok   { display: inline-block; vertical-align: bottom; white-space: pre-wrap; }
.chord { display: block; font-size: var(--chord-size); line-height: 1.1;
         font-weight: 600; color: var(--chord-color); }
.lyr   { display: block; font-size: var(--lyric-size); line-height: var(--line-height); }
```

Почему так, а не SVG: перенос строк, колонки, печать и выделение текста работают сами,
без пересчёта при resize/смене шрифта. Текст остаётся текстом — ищется браузером, доступен
скринридеру, копируется.

**Правила разрыва строк:** `.tok` — атомарен (`display:inline-block` уже не даёт разорвать пару).
Разрыв возможен только **между** токенами. Поэтому токен должен резаться по границе слова:
если после аккорда идёт `уж скорбей»`, токен = `[G]уж` + отдельный токен ` скорбей»`.
Правило: **токен заканчивается на первом пробеле после маркера**.

**Коллизия «длинный аккорд над коротким слогом»** (`[Cmaj7/G]а`): токен просто становится
шире слога — это нормально и так делает OnSong. Никакой компенсации не добавляем.
Единственная страховка: `.chord { padding-right: 0.4ch }`, чтобы соседние аккорды не слипались.

### 3.3 Режим «только текст»

`.chord { display: none }` — одна строка CSS, без второго рендер-пути.

### 3.4 Типографика аккорда (не потерять при переписывании)

Текущий `ChordRenderer.tsx` разбирает аккорд на составляющие — нота, модификатор
(`maj7`, `sus`, `dim`), альтерация, бас после `/` — и стилизует их по-разному.
Это заметно улучшает читаемость с расстояния и **должно сохраниться**: при замене
рендера на токен-модель токенизатор аккорда переносится как есть, меняется только
то, как токен встраивается в строку.

### 3.5 Шапка песни

Заголовок, `{subtitle}`, темп, размер — и **действующая тональность** с указанием
её источника (см. §10.1). Шапка скрывается тумблером (§5) и не печатается повторно
на второй колонке.

## 4. Колонки и постраничный режим

### 4.1 Две колонки без страниц бессмысленны

Проверено на реальном планшете: если контент выше экрана, музыкант доигрывает левую
колонку, **скроллит вверх** к началу правой, потом снова вниз. Это хуже одной колонки.
Поэтому две колонки существуют только вместе с постраничным режимом:
**страница = экран**, колонки заполняются по очереди доверху, переход — перелистыванием.

Так устроен pagination mode в OnSong и то, что WorshipTools называет «минимизировать
смену страниц».

### 4.2 Основной режим планшета — листы вниз (`sheets`)

Проверено на iPad: **горизонтальный свайп во время игры ненадёжен** — рука занята,
жест уходит вбок, легко промахнуться на полстраницы. Вертикальное движение попадает всегда.

Поэтому страницы выкладываются **стопкой вниз**: лист, стык, следующий лист.
Скролл свободный (без snap) — музыкант может замереть на стыке и видеть низ одного листа
и верх следующего. Внутри листа — обычные 1–2 колонки, скролла внутри нет.

**Техника: лист — это окно, вырезающее свою страницу из одинаковой копии песни.**

```html
<div class="sheet">                       <!-- height = высота страницы, overflow: hidden -->
  <div class="sheet-flow"                  <!-- одинаковая для всех листов вёрстка -->
       style="width: {W}px; transform: translateX(-{i * pitch}px)">…песня целиком…</div>
</div>
```

Браузер по-прежнему сам решает, где резать (`column-fill: auto` + фиксированная высота);
мы только клипируем нужную страницу. Расчёта высот нет — `columnHeightCalculator`
остаётся удалённым.

**Три подводных камня — каждый стоил бага в прототипе:**

1. **Шаг страницы = `clientWidth + column-gap`, а не ширина.** После последней колонки
   страницы идёт gap, поэтому следующая пара колонок начинается с `W + gap`. Сдвиг
   на голую ширину копит лишний отступ слева на каждом листе и завышает их число
   (появляется пустой хвостовой лист). Тот же расчёт нужен и для `scrollLeft` в §4.4.
2. **Типографика клона обязана совпадать с источником до пикселя.** В прототипе клоны
   лежали вне контейнера, задающего `font-size`, унаследовали 16px вместо 12px и
   разбились иначе — получились пустые листы. Клон должен наследовать те же
   `font-size` / `font-family` / `line-height`.
3. **Число страниц считать по правому краю последней секции**, а не по `scrollWidth`:
   multicol резервирует пустую хвостовую колонку.
   `total = ceil((maxSectionRight - 2) / pitch)`.

Перестраивать листы нужно на **каждое** изменение раскладки: колонки, размер шрифта
(с дебаунсом ~120мс), высота области, поворот экрана, режим «только текст».

**Верхний отступ листа задавать через `box-sizing: content-box`**, иначе поле съест низ
страницы: `height` должен равняться высоте потока, а padding идти плюсом.

**Проверено (Chromium 1024×1366 + iPad Safari, реальные песни корпуса):** пустых листов
нет ни в одной комбинации (1/2 колонки × высота 60vh/75vh/экран × шрифт 12/18/30),
левый край всех листов совпадает, содержимое продолжается без потерь и дублей
(«Вступление…Проигрыш» → «Куплет 3…Припев» → «Куплет 4…Инструменты»).
Тестовая страница — `docs/song-viewer-prototype.html`, режим «листы ↓».

### 4.3 Оформление стыка

Стык должен читаться как переход на новый лист, а не как случайный разрыв:

- зазор 12–16px, в котором виден фон подложки (лист светлее, «стол» темнее);
- волосяная линия сверху каждого следующего листа;
- отступ сверху внутри листа ~18px, чтобы текст не начинался вплотную к стыку;
- номер «2 / 3» в углу листа.

### 4.4 Горизонтальные страницы (`paged`) — второй режим, под педаль

Тот же механизм без клонирования: один поток, `flow.scrollLeft += pitch`.
Нужен тем, кто играет с Bluetooth-педалью, где жест не важен вовсе.

| Способ | Зачем |
| :--- | :--- |
| `→` / `пробел` / `PageDown`, `←` / `PageUp` | **Bluetooth-педали** (AirTurn, PageFlip) шлют именно эти коды — поддержав клавиши, получаем педали бесплатно |
| тап по правой/левой трети экрана | когда руки заняты инструментом |
| кнопки в панели | доступность и мышь |

Индикатор «2 / 3» обязателен в обоих постраничных режимах: он превращает размер шрифта
в осмысленный инструмент — музыкант крутит шрифт, пока песня не уляжется в 1–2 листа.
Это и есть замена зуму.

### 4.5 Режимы и их совместимость

| Режим | Устройство | Колонки | Движение | Автоскролл |
| :--- | :--- | :--- | :--- | :--- |
| `scroll` | телефон, по умолчанию | 1 | вертикальный скролл | да |
| `sheets` | планшет, по умолчанию | 1 или 2 | вертикальный скролл по листам | нет |
| `paged` | планшет, опция | 1 или 2 | перелистывание вбок | нет |

Автоскролл живёт только в `scroll`: в постраничных режимах он дерётся за ту же ось,
что и переход между листами. Кнопка автоскролла там скрыта.

Переключатели режима и числа колонок — **явные** (как в WorshipTools), не авто по ширине.
На узком экране (`< 640px`) «2 колонки» дизейблятся с подсказкой «доступно на планшете».
Значения персистятся на устройство (§7).

### 4.6 Разрывы

`break-inside: avoid` ставится и на секцию, и на **строку** — иначе аккордовая надстрочная
часть может уехать на следующий экран отдельно от своего текста.

Секция выше экрана всё равно разорвётся: это допустимо, автопроверка на тестовой странице
такие секции считает и показывает предупреждение. Лечится уменьшением шрифта самим
музыкантом. `{column_break}` из стандарта ChordPro не поддерживаем: в корпусе не встречается.

**Чего не делаем:** не балансируем колонки вручную, не считаем высоты в JS, не переносим
секции скриптом. Именно из этого выросла известная жалоба пользователей WorshipTools
на «пустое место в 2-колоночном режиме».

## 5. Размер шрифта вместо зума

Один слайдер `--lyric-size` (12–32px, шаг 1). Остальное — производные CSS-переменные:

```css
.sheet {
  --lyric-size: 18px;
  --chord-size: calc(var(--lyric-size) * 0.82);
  --line-height: 1.45;
  --section-gap: calc(var(--lyric-size) * 1.2);
}
```

Дополнительно (по образцу OnSong, где «влезаемость» решают межстрочником и шапкой):

- переключатель **плотности**: `comfortable` / `compact` — меняет `--line-height` (1.45 / 1.2)
  и `--section-gap`;
- тумблер **«скрыть шапку»** — убирает title/subtitle/метаданные, освобождая экран.

Зум жестами в режиме чтения **отсутствует полностью**. Pinch на листе не перехватывается.

## 6. Режим рисования (единственное место с зумом)

Отдельный слой поверх листа, включается кнопкой. Пока он активен:

- лист замораживается (`position: sticky` на скролл-контейнере, скролл выключен);
- зум/пан живут **только в этом слое** через `transform` на обёртке слоя;
- зум **не персистится** — при выходе из режима сбрасывается в 1.

**Хранение штрихов — критично для совместимости с reflow.**
Экранные координаты нельзя: смена шрифта или числа колонок сдвинет всё.
Штрих хранится привязанным к якорю:

```ts
type Stroke = {
  anchor: { sectionIndex: number; lineIndex: number };  // к какой строке привязан
  points: Array<[x: number, y: number]>;  // px относительно bounding box строки-якоря
  color: string;
  width: number;
};
```

При рендере штрих позиционируется от актуального `getBoundingClientRect()` строки-якоря.
Библиотека — `perfect-freehand` (остаётся, это и есть проверенное решение).

**Ограничение, принимаемое осознанно:** при смене размера шрифта штрихи сдвигаются вместе
со строкой, но не масштабируются. Для пометок «повтор ×2», «стоп» — приемлемо.

## 7. Настройки и персист

| Настройка | Значения | Скоуп |
| :--- | :--- | :--- |
| `mode` | `scroll` \| `sheets` \| `paged` | устройство (§4.5) |
| `columns` | `1` \| `2` | устройство (localStorage) |
| `fontSize` | 12–32 | устройство |
| `density` | `comfortable` \| `compact` | устройство |
| `showChords` | bool | устройство |
| `showHeader` | bool | устройство |
| `key` | тональность, строка (`"Ab"`) | **на песню, на пользователе** (Directus), см. §10 |
| `strokes` | `Stroke[]` | **на песню, на пользователе** (Directus) |

Разделение важное: раскладка — свойство устройства (планшет и телефон разные),
тональность и пометки — свойство музыканта и едут за ним между устройствами.

**Идентификатор песни — integer `id`** (решение от 2026-07-25, отменяет более ранний
черновик этой спеки, где требовался `slug`).

Наружу (URL `?id=…`, ключ офлайн-кэша в IDB, внешние ключи `setlist_items.song`,
`song_user_state.song`) идёт `songs.id`. Поле `songs.slug` в схеме остаётся и заполняется
импортёром, но идентификатором не служит.

Обоснование: текущий код (BFF `GET /songs/:id`, IDB-стор `songs`, `?id=` в роуте,
`downloadManager`) уже целиком построен на `id`. Переход на `slug` менял бы ключ
IDB-стора, что делает уже скачанные офлайн-записи недостижимыми и требует bump
`DB_VERSION` с очисткой стора, записи `manifest['songs']` и `apiCache['songs:list']` —
иначе список отрисуется из старого кэша, а деталь не откроется (класс бага
«рассинхрон list↔detail», см. офлайн-инварианты в `CLAUDE.md`). Цена не оправдана.

**Принятый риск:** при пересоздании коллекции `songs` в Directus integer `id` поедут
и утащат за собой битые ссылки и офлайн-кэш. Митигация — не пересоздавать коллекцию,
а мигрировать; при переимпорте песен сохранять существующие `id`.

## 8. Автоскролл

`requestAnimationFrame` → `container.scrollTop += px`, где `px` считается из
`speed` (строк в минуту) и текущего `--line-height`. Никаких `transform`, никакой
анимации CSS — только нативный скролл, чтобы пользователь мог в любой момент
перехватить пальцем.

- Скорость: 5 фиксированных ступеней + запоминание последней.
- Любой `touchstart`/`wheel` по контейнеру → пауза; возобновление — кнопкой.
- При достижении низа — стоп (не зацикливать).
- Скорость персистится **на песню** (у медленной песни свой темп).

## 9. Печать и PDF

Один и тот же DOM, отдельная таблица стилей:

```css
@media print {
  @page { size: A4 portrait; margin: 12mm; }
  .sheet { --lyric-size: 11pt; --chord-size: 9pt; columns: 2; }
  .toolbar, .fab, .drawing-layer { display: none; }
  .section { break-inside: avoid; }
}
```

Никакого отдельного «A4-вьювера», никакой fit-математики. PDF = печать в PDF браузером.
Экспорт всего сетлиста = одна страница со всеми песнями подряд + `break-before: page`
на каждой песне.

## 10. Тональности и транспозиция

### 10.1 Три уровня тональности

Одного числа «сдвиг в полутонах» недостаточно. У песни три разных тональности,
и путать их нельзя:

| Уровень | Где живёт | Кто меняет | Смысл |
| :--- | :--- | :--- | :--- |
| **исходная** `originalKey` | `songs.song_key` | вместе с текстом песни | в ней записаны аккорды в `content` |
| **основная** `defaultKey` | `songs.default_key` (новое поле) | `musician_editor` | в ней команда обычно играет |
| **рабочая** `key` | `setlist_items.key` / `song_user_state.key` | любой музыкант | на это служение / лично для себя |

**Разрешение действующей тональности** (первое непустое):

```
effectiveKey = personalKey ?? setlistItemKey ?? defaultKey ?? originalKey
```

- `defaultKey` пустой ⇒ равен `originalKey`. Заполнять его при импорте не нужно.
- Открыл песню из сетлиста — работает `setlist_items.key`. Открыл из общего списка —
  `defaultKey`. Личная тональность перебивает всё, но **только для этого пользователя**.
- В UI видно, что применено: «Соль (по умолчанию)» / «Ля (сет: Воскресенье 3 авг)» /
  «Ля-бемоль (моя)» + кнопка «сбросить».

### 10.2 Хранить тональность, а не полутона

`key` — строка (`"G"`, `"Ab"`, `"F#m"`), не `int`. Сдвиг вычисляется в момент рендера:

```ts
const semitones = Interval.semitones(Interval.distance(originalKey, effectiveKey));
```

Причина: полутона не отвечают на вопрос энгармонии. `+3` от `C` — это `D#` или `Eb`?
От тональности ответ однозначен: `Eb` ⇒ пишем бемоли (`Ab`, `Bb`), `D` ⇒ диезы (`F#`, `C#`).
Если хранить offset, спеллинг приходится угадывать эвристикой — и получать претензии
музыкантов на `A#` вместо `Bb`.

Правило спеллинга: набор знаков берётся из **целевой тональности** через
`Key.majorKey(effectiveKey)` / `Key.minorKey(...)`, а не из направления сдвига.

### 10.3 Правила транспозиции токенов

`@tonaljs` (`Note.transpose`, `Chord.get`, `Key.*`) — остаётся.

- Транспонируются токены `kind: 'chord'`; `bar` и `note` — нет.
- Цепочка `[E-B/D#-E/D]` — сплит по `-`, транспозиция каждого, сборка обратно.
- Бас после `/` транспонируется отдельно (`C/G` → `D/A`).
- Нераспознанный токен возвращается **без изменений** (не падать на `[C#mсть.]`).
- Мажор/минор целевой тональности берётся из **исходной**: если `originalKey = Em`,
  а музыкант выбрал «Соль» — это `Gm`, а не `G`. В UI выбор тональности показывать
  в том же ладу, что исходная.

### 10.4 Каподастр — вне v1

`{capo:}` в корпусе не встречается ни разу. Поле `capo` в `setlist_items` завести
(гитаристы попросят), но UI и логику «показывать аккорды как с каподастром» не делать,
пока не попросят явно. Транспозиция полностью её заменяет для v1.

## 11. Доступность и мобильный ввод

- Лист — обычный текст в потоке: работает выделение, поиск по странице, скринридер
  читает лирику (аккорды помечены `aria-hidden` в режиме «только текст»).
- Тап-таргеты панели — ≥ 44px.
- Свайп между песнями сетлиста — только по горизонтали и только когда горизонтального
  скролла нет (в reflow-модели его нет никогда — упрощение относительно текущего кода,
  где свайп конфликтовал с зумом).
- `prefers-reduced-motion` → автоскролл стартует без плавного разгона.

## 12. Критерии приёмки

Тестовый корпус — 6 песен, покрывающих экстремумы:

| Файл | Что проверяет |
| :--- | :--- |
| `1-аллилуйя-наш-спаситель` | аккорды внутри слова, типографские кавычки, `[\|]` |
| `45-святая-ночь` | самая плотная строка (110 симв., 7 токенов) |
| `66-на-кресте-совершилось-всё` | 42 аккордовые строки подряд |
| `64-его-слава-благо-мне` | самая длинная песня (101 строка) — 2 колонки |
| `13-гимн-небесный` | длинные строки, тире и спецсимволы |
| песня с `[(пауза)]`, `[E-B/D#-E/D]`, `[C#mсть.]` | нестандартные токены, отказоустойчивость |

**Unit (vitest):**
- токенизатор: все 5 видов токенов, аккорд внутри слова, разрыв токена по пробелу;
- транспозиция: цепочки, бас-ноты, битые токены, выбор диез/бемоль;
- тональности: разрешение `personal → setlist → default → original` (все 4 ветки + пустой
  `defaultKey`), сохранение лада (`Em` + «Соль» = `Gm`), спеллинг по целевой тональности
  (`Eb` даёт `Ab`/`Bb`, `D` даёт `F#`/`C#`);
- парсер секций: `{comment:}` как разделитель, песня без единого `{comment:}`.

**E2E (playwright, уже настроен в bible-plan):**
- листы: **ни одного пустого листа** во всех комбинациях (1/2 колонки × три высоты ×
  шрифт 12/18/30) — это ловит и ошибку шага, и рассинхрон типографики клона;
- листы: левый край содержимого одинаков на всех листах (ловит дрейф на `column-gap`);
- листы: содержимое непрерывно — множество секций на листах не пересекается,
  их объединение равно всем секциям песни;
- листы: низ последнего листа не обрезан (`flow.bottom == sheet.bottom`);
- постраничный режим: перелистывание сдвигает ровно на `clientWidth + column-gap`,
  `scrollHeight == clientHeight`, счётчик страниц совпадает с фактическим числом;
- педали: `→`, `пробел`, `PageDown` листают вперёд, `←`, `PageUp` — назад;
- автоскролл недоступен в `sheets` и `paged`;
- 1 ↔ 2 колонки: нет горизонтального скролла ни в одном режиме, на 390px и 1024px;
- смена размера шрифта: нет горизонтального переполнения на границах 12 и 32px;
- автоскролл: доезжает до низа и останавливается; тач прерывает;
- рисование: штрих остаётся на своей строке после смены размера шрифта;
- печать: `page.pdf()` даёт 1–2 страницы A4 для 5 из 6 тестовых песен.

**Ручная проверка (не автоматизируется):**
- iPad Safari: multicol внутри скролл-контейнера — исторически глючное место;
- реальный планшет на репетиции: читаемость с расстояния 60–80 см в 2 колонках.

## 13. Что осознанно не делаем

- Диаграммы аккордов (`{define}`, гриф) — в корпусе нет, команде не нужны.
- Nashville-номера — потом, если попросят (в модели уже возможно: это функция от токена).
- Пагинацию «как бумага» на экране — reflow вместо неё.
- `chordsheetjs` — GPL-2.0-only (весь bible-plan пришлось бы открывать под GPL),
  27 МБ unpacked, и колонки у него явно вне скоупа. Свой токенизатор ≈ 120 строк.
- Зум в режиме чтения — см. §5.
